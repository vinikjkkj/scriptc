Store-Mongo's 238

store-mongo does not reach a binary because we do not fully compile the mongodb driver. This is what its 238 blocker sites actually are — and why fixing the largest cause makes the number go up.

Where the 238 live

226 of them are not our code

The honest sentence is “we do not fully compile the mongodb driver”, not “the store package is broken”. @zapo-js/store-mongo's own source contributes exactly one site, and that one is cascade off two mongodb types it names in a config union.

The largest cause

One line gates the entire operations subsystem

Over half of mongodb's sites sit downstream of a single field declaration in src/operations/command.ts: 

// mongodb/src/operations/command.ts:93
export abstract class CommandOperation<T> extends AbstractOperation<T> {
  override options: CommandOperationOptions;

A class field redeclared at a different record shape. The compiler refuses it — “these layouts give the property one slot, and one slot cannot answer both spellings” — and everything below it falls:

6redeclaring inherited fields at a different type — one per instantiation
↓ so CommandOperation<T> has no compiled concrete instantiation
22extending the generic class 'CommandOperation' without a compiled concrete instantiation
↓ so DeleteOperation, InsertOperation, UpdateOperation… are not classes in the program
9extending classes not declared in the program — carrying no cascade code
32SC2004 uses of 'AggregateOperation' inherit the blocker on its declaration

Fourteen lines of plain TypeScript reproduce the whole chain, message for message, with no mongodb in sight. Five sibling probes narrow it: an initializer does not help, it is not about genericity, and the already-shipped undefined-arm removal case still works. The gate is precisely a field redeclared at a record whose member set or member optionality differs from the inherited one.

P1 and P2 are exactly additive and clear nothing downstream — so this.constructor and response.toObject are not gates on the extends family. P5a is. One token on one line clears 19 of the 22 extends refusals, without touching operation.ts at all.

One arm was wrong, and the instrument said so. P2's first substitute returned a record that did not satisfy TResult: 8 sites cleared and 7 new ones appeared at the same line. A thin stub does not isolate a variable, it changes the program — visible only because the differ reports site identities, never counts.

And the rig itself failed a control first. The launcher set the probe cache in the environment, and the runner re-sourced the environment file and reset it — so all six arms read the unpatched tree and each reported a perfect 0 cleared, 0 added, which reads exactly like “this line is not the cause”. Every arm now asserts, from its own output record, which tree produced it.

The finding that reframes the objective

238 is a floor, not a work estimate

Arm P4 removes the largest cause in store-mongo. It clears 41 sites and adds 73.

24 of those are artifacts of removing the declaration rather than fixing it. The other 49 are real — refusals inside the 22 operation classes that had never been analysed, because a class the compiler refuses to instantiate never has its body walked. Seventeen of the 49 are more of the same cause.

The honest arithmetic is 242 − 41 + 49 = 250. The blocker count is suppressed by the refusals themselves: every refusal hides its own subtree. P4, P5a and P5b expose the identical 73 sites by identity, which is the cross-check that command.ts:93 alone causes the exposure.

This means no count of blocker sites — this one included — can be read as an estimate of remaining work, and it means progress on this objective will look like regression on the dashboard for a while.

The build

“1 error” was hiding 237

The build stops at a single error and never reaches lowering: SC1012 export = in @mongodb-js/saslprep. Routed past that one module-link refusal, the build runs to completion and prints its whole list for the first time — and it matches the survey exactly.

It still says nothing about the IR validator or either emitter: that build errored before lowering. A closed site count is still not a build.

The shortest path, honestly

There isn't a short one, and part of it isn't ours

Two packages on store-mongo's critical path publish no provenance attestation, so the compiler cannot reach their source at all: whatwg-url@14.2.0, which MongoClient needs to parse a URI, and sparse-bitfield@3.0.3 under saslprep. Neither is a package we control.

The --npm-static escape was tested rather than assumed, and the compiler named its own reasons. It is not shut — it is a short chain of small packages deeper.

Ranked by what was measured, the route to a binary is: those two attestations (or a compiler that follows a published .esm-wrapper.mjs to its CommonJS sibling); the parked class X extends URL, which store-mongo cannot route around; the redeclared-field slot; the ~49 sites behind it and whatever they expose; and a 65-site representation bucket, each item with semantics attached.

The redeclared-field slot is the one worth naming carefully. 71 of mongodb's 87 redeclared fields would be served by a single slot holding the union of both member sets. But the obstacle is in the compiler's own source, not a guess: a narrowing conversion in the record model copies, so one slot cannot serve two spellings by coercion. Fixing it means a non-copying narrowing view for field slots — the record layout, the IR, the validator and both emitters. That is expensive, and it is the user's call, not this block's.

Found while measuring

Six things nobody was looking for

  • The provenance cache extracts 2.1 GB to compile 2 MB. mongodb's attested checkout is 2,157 MB — docs/ is 1,247 MB and test/ is 865 MB. src/ is 2 MB. All five checkouts minus those two directories is 23.4 MB and produces a site-for-site identical analysis.
  • Only 5 of 17 packages are source-mapped, and one was dropped by a cap — @zapo-js/native: skipped — provenance package limit (16) reached.
  • The spec-twin fix already on main closed store-mongo's entire zapo-side cluster. Diffed by site identity, the default lane clears exactly those 7 sites and adds 3 in cmap/connection.ts the old lane never reached.
  • this.constructor is filed beside Date and WeakMap under “standard library surface with no lowering”, because constructor is an Object.prototype member. Mechanically it is a lowering, not a representation decision — any triage bucketing by diagnostic code puts it in the wrong pile.
  • --npm-static compiles a package's implementation without making its exported type representable. sparse-bitfield reads static, and the site that depends on its type is unchanged.
  • Two hypotheses of mine, both refuted by their own probes and withdrawn. bson's five SC1043 sites are not a mis-attributed location, and the redeclare message's “without an initializer” clause is not misleading — it is dropped when an initializer is present.

Every instrument is committed under tests/perf/mongodriver/ and negative-controlled in both directions: the differ self-diffs to 0/0/0, reports 3 cleared for 3 dropped sites, and reports 5 moved — not 5 cleared plus 5 added — for 5 sites shifted by four lines. The patcher refuses any path outside a probe directory, so every attested checkout was only ever read; the classifier prints UNCLASSIFIED and exits non-zero rather than folding anything silently, and it is 0.

Reported numbers are the default configuration. The substitution arms ran with SCRIPTC_PROVENANCE_SPEC_TWINS=off, and that lane's relationship to the default one is measured, not assumed.
