A clean census is NOT a green build. analyze() stops before

yields no linkable artifact — the recovered module is missing whole
statements, so the emitter reports and then rethrows the first refusal.
"WeakMap alone puts zapo-js 1.8.2 on the LLVM tier" is therefore a
PREDICTION that only a post-fix STRICT build can settle, and it will be
settled by the artifact — a .ll and no .c — not by the census and not by
the absence of a refusal message.

WHY I MISSED IT, WHICH IS THE PART WORTH KEEPING:

  I reasoned about WeakMap as a feature and asked which other FEATURES
  1.8.2 had gained. truthy:union:keyobj is not another feature. It is
  the second half of the same idiom:

      const cached = privateKeyObjectCache.get(privKey);  // weakmap:intrinsic
      if (cached) { return cached; }                      // truthy:union:keyobj

  `get` on a WeakMap<Uint8Array, KeyObject> answers `KeyObject |
  undefined`, so the truthiness test on the NEXT LINE is what reads the
  lookup. Both refusals are in the same function (%m50.x25519Private-
  KeyObject) and the census said so in the `fn` column, which I could
  have read as the clue it was. A WeakMap whose values are handles
  arrives WITH a truthiness test on those handles; closing one without
  the other moves the wall down one line.

  The general form: a "delta between versions" model finds new features
  and is blind to the constructs those features DRAG IN. Reach is not
  per-construct, it is per-idiom.

AND THE THIRD REFUSAL WAS NOT A DELIBERATE ONE, WHICH HAD TO BE CHECKED:

  Cluster 9 exists for refusals that prevent a WRONG ANSWER, and
  truthy:union:jsval|dyn are in it. keyobj is not. There are TWO sets
  and they differ by exactly the five crypto/key handles:

    REF_TRUTHY_KINDS           may a BARE value be lowered at toBool?
                               a policy question, owned by the frontend
                               and ir/validate.ts
    UNION_ARM_JS_OBJECT_KINDS  is this ARM's payload a JS object?
                               a fact, and the only question a per-union
                               truthiness helper asks

  The C backend's unionTruthyHelper reads the SECOND and answers
  `return true`. The LLVM site read the FIRST. So this was a one-token
  drift between two lanes, not a correctness fence — and the comment
  sitting on that very line already described both sets without noticing
  it was reading the wrong one.
