2. POPULATION OF THE 4,376 CLASS -- HCPKSIZE (peak) vs HCSIZE (shutdown)

   run  arm  peak blocks   peak bytes   b/blk   shutdown blocks
   p1   SL         1570      7259680    4624   ABSENT
   p2   FB         1157      5349968    4624   ABSENT
   p3   FB         1197      5534928    4624   ABSENT
   p4   SL         1845      8531280    4624   ABSENT
   p5   SL         1470      6797280    4624   ABSENT
   p6   FB         1293      5978832    4624   ABSENT

   b/blk is 4624, NOT 4376: scr_heap_census.h:167 accumulates
   `size + overhead` from PROCESS_HEAP_ENTRY, and this class carries
   248 B of CRT heap overhead per block (5.66%). A `count x 4376`
   figure understates the committed footprint by exactly that much.

3. THE CEILING, AND WHETHER IT BINDS

   szAlloc   = 4096 + 216 + 56 = 4368   (sqlite3.c:58472)
   CRT block = szAlloc + 8          = 4376   (sqlite3.c:28035)
   numberOfCachePages (sqlite3.c:57021) divides by PCache's own
   szPage + szExtra = 4096 + 136 = 4232, NOT by szAlloc.

   cache_size   pages/conn   max peak population   binds?
   -2000              483                  1845   YES
   -16000            3871                  1845   no

   stackless peak mean 1628.3 blocks; fiber peak mean 1215.7.
   The SHIPPING ceiling (-16000 => 3871 pages/connection)
   sits above every run: the largest peak population, 1845, is
   47.7% of it. The knob is NOT what bounds
   this population at the peak.
   Stock SQLite's -2000 (483 pages) WOULD bind, at 26.2% of the
   measured peak -- which is the trade scr_async.c:2498-2505 records as
   already measured and rejected (+6.65 ms/request, +74.1%).

   Two blocks in all six runs, at the peak AND at shutdown, both arms:
   this population does not scale with the load. It is reported as a
   SIZE class, not as an identification -- the peak census carries no
   site id, so nothing here names which SQLite caller owns those two.
