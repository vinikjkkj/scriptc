# `HCSIZE 131079` has an owner, and half of it is alignment padding

> **What this answers.** `DECOMP-ON.md` §4 names a row — *"46 blocks,
> 6,030,160 B, 31.89% of the arm's busy heap"* — and ends with *"It is named
> in no document in this repository."* §6 then orders attribution and says it
> *"must come from the HeapWalk side — reading the contents of a live
> 131,079-byte block"*. **It did not need a run.** The row closes by source
> arithmetic alone, the arithmetic is exact to the byte against four
> committed censuses, and an already-instrumented site brackets the count
> independently. **Nothing was built, nothing was re-run, and no instrument
> was added for this file.**

Evidence consumed: `evidence-idle/{off,on,long,half-on}.{heapcen,prof}.txt`
at `715408cf0`, the sources as committed, and the mingw-w64 aligned-malloc
implementation shipped inside the pinned toolchain.

## 0. The owner, in one chain

```
scr_string.c "64 KiB-aligned, because scr_str_ar_chunk_of masks"
  scr_str_chunk_alloc(), _WIN32 arm:
      return _aligned_malloc(SCR_STR_ARENA_CHUNK, SCR_STR_ARENA_CHUNK);
  SCR_STR_ARENA_CHUNK = ((size_t)64 << 10) = 65,536

_aligned_malloc(s, a) -> _aligned_offset_malloc(s, a, 0), whose body is
  (mingw-w64 misc/mingw-aligned-malloc.c, __mingw_aligned_offset_malloc)
      #define GAP(offset) ((0 - offset) & (sizeof (void *) -1))
      alignment--;
      p0 = malloc (size + (alignment + GAP (offset) + sizeof (void *)));

  offset = 0  ->  GAP(0) = 0
  alignment-- ->  65,535
  request     =  65,536 + (65,535 + 0 + 8)  =  131,079
```

**`HCSIZE 131079` is one 64 KiB string-arena chunk per block.** Forty-six of
them on `off`/`on`/`long`, thirty-three on `half-on`.

The same arithmetic is in UCRT's `_aligned_offset_malloc`
(`nonuser_size = alignment + sizeof(uintptr_t) + gap` over a decremented
alignment) — both descend from the one published algorithm — so the number
does not depend on which CRT the `x86_64-windows-gnu` link resolves
`_aligned_malloc` to. That matters here: `malloc.h` declares it `_CRTIMP`,
and `ucrtbase-common.def.in` exports it, so the mingw static copy is not
automatically the one that runs. **Both candidates compute 131,079.**

### `131079 mod 8 = 7` is the fingerprint, not an obstacle

`DECOMP-ON.md` §4(b) killed `scr_string.c:1162` with *"131,079 mod 8 = 7. No
`scr_pool_bytes()` result can be odd."* That argument is right, and it points
at the answer rather than away from it: the padding term
`alignment - 1 + sizeof(void *)` is **≡ 7 (mod 8) for every power-of-two
alignment ≥ 8**. A request of the form `n*8 + (2^k - 1) + 8` cannot be
anything but an aligned-allocator gap. **The owner and the excluded site are
in the same file, 409 lines apart.**

## 2. Why the profiler cannot see it: the libc hole, named

`scr_prof.h` interposes **four names and only four**, at its end, under the
comment *"The macros go last, so every definition above still calls the real
libc entry point"*:

```
#define malloc(n)      scr_prof_malloc((n), SCR_PROF_SITE)
#define calloc(a, b)   scr_prof_calloc((a), (b), SCR_PROF_SITE)
#define realloc(p, n)  scr_prof_realloc((p), (n), SCR_PROF_SITE)
#define free(p)        scr_prof_free((p), SCR_PROF_SITE)
```

`_aligned_malloc` is not one of them, and the `malloc` it calls is compiled
inside the CRT, where no `-include` of this repo's headers reaches. So the
allocation is invisible on the `PROF` side — and its `_aligned_free` partner
is invisible too, which is why nothing in the prof table is even *imbalanced*
by it. The CRT allocates on the process heap, which is heap 0, which is
exactly the heap `scr_heap_census.h` walks. **Visible to the census,
invisible to the profiler, by construction.** That is `scr_prof.h`'s own
*"What it does NOT cover is an allocation inside libc"*, instantiated.

### The standing audit this leaves behind

Any CRT entry point that allocates but is not spelled `malloc` / `calloc` /
`realloc` / `free` is outside the prof lane. The complete list of such
callers in the tree today, and what each is:

| call | where | status |
|---|---|---|
| `_aligned_malloc` / `_aligned_free` | `scr_string.c`, `scr_str_chunk_alloc` / `scr_str_chunk_free` | **this row** |
| `posix_memalign` | `scr_string.c`, the non-`_WIN32` arm of `scr_str_chunk_alloc` | not this target; **and it wastes nothing** (§5) |
| `_wcsdup` | `scr_watch.c`, twice in the watch setup | invisible, small, not on this workload |
| `strdup` | `scr_tls.c`, `c->hostname` | invisible, small; no `scr_tls.c` row exists in any arm's `PROF` |
| `realpath` | `scr_lib.c`, twice | **not an allocation** — both pass a caller buffer |
| `mmap` | `scr_cycle.c`, `scr_array.c` | VM reservations, not CRT-heap blocks |

## 3. The coverage hole `DECOMP-ON.md` §4 left open is now closed too

§4's hole 1 is *"The emitted program's own translation unit"*, left standing
as *"real and probably not this owner"* on the evidence that the literal
`131072` does not occur in the 242 MB `.ll`. That is an argument about a
literal, and it is replaceable by an argument about alignment, which is
stronger:

* `zapo-rest.ll` declares exactly two raw allocators, `@calloc` and
  `@malloc`, and **no** `@realloc`, `@_aligned_malloc`, `@HeapAlloc`,
  `@VirtualAlloc` or `@strdup`.
* It makes **835 calls** to those two, and **835 of 835** have the shape
  `i64 ptrtoint (ptr getelementptr (%T, ptr null, i32 1) to i64)` — that is,
  `sizeof(T)` for a named LLVM struct type, never a runtime-computed size.
* Of 2,409 emitted `%sc_*` type definitions, every one either begins with
  `i64` or contains a `ptr`, so **every one has alignment 8 and a size that
  is a multiple of 8**. The largest array appearing inside any type
  definition is `[270 x ...]`.

**No request the emitted TU can make is ≡ 7 (mod 8), and none of them is
within two orders of magnitude of 131,079.** The hole is real for other
questions; it is shut for this one.

Hole 3, *the operating system*, is untouched by this file and was not needed.

## 4. An independent bracket, from a site that IS instrumented

`scr_str_ar_index_add` keeps one index entry per chunk and grows it by
doubling from 32:

```
    size_t cap = scr_str_ar_capindex ? scr_str_ar_capindex * 2u : 32u;
    ScrStrChunk **n = (ScrStrChunk **)realloc(scr_str_ar_index, cap * sizeof *n);
```

`realloc` **is** interposed, so this line is in `PROF` — and it reads the
same in all four arms:

```
PROF 2 768 0 0 0 ... scr_string.c:726
PROFHIST ... 8:1 9:1 ... scr_string.c:726
```

Two reallocations, 768 bytes, one in octave 8 and one in octave 9 — that is
`32 x 8 = 256` then `64 x 8 = 512`, and `256 + 512 = 768`. The index
therefore crossed 32 entries and never reached 65.

**33 ≤ chunks ever indexed ≤ 64, in every arm.** The census says 46 live on
`on`/`off`/`long` and **exactly 33** on `half-on` — the lower edge of the
bracket, which is where it must be, because `half-on` had to cross 32 to
produce the second realloc at all. An instrumented site and an
uninstrumented one agreeing to the edge of an interval is the independent
witness this attribution would otherwise lack.

## 5. The alignment has no consumer: the lever

The chunk is 64 KiB-aligned because an earlier design derived a block's chunk
by masking its address. That design was replaced; the alignment was not. Both
comments are still in the file, and they contradict each other:

* `scr_string.c`, the per-chunk accounting note: *"THE CHUNK IS DERIVED FROM
  THE BLOCK BY A MASK, NOT A SEARCH, which is the whole reason the chunks are
  now 64 KiB-ALIGNED rather than plain malloc."*
* `scr_string.c`, the note on `scr_str_ar_chunk_of`, 34 lines later: *"A MASK
  WOULD HAVE TO DEREFERENCE WHAT IT FINDS, and that is why this is a
  search."*

The code agrees with the second. `scr_str_ar_chunk_of` is a binary search
over `scr_str_ar_index`, sorted ascending by address; its only two callers
are in the idle drain. And the search is the whole mechanism: `h->magic` is
**written** when a chunk is born and **cleared** when it dies, and there is
no read of it anywhere in the tree — so the *"magic plus a range test"* the
first note describes is not performed either.

**Nothing in `packages/` or `tests/` masks a pointer by
`SCR_STR_ARENA_CHUNK - 1` or by `~0xFFFF`.** Positive control for that
search: the same pattern class finds the two masks that do exist in
`scr_string.c`, both of them hash-table index masks on `w - 1u`, neither of
them on an address. A scan that cannot find a mask it is pointed at is not a
scan.

So the Windows arm can be plain `malloc` / `free`, exactly as the carve
arithmetic already assumes:

| | blocks | bytes | share of 18,907,440 |
|---|---:|---:|---:|
| today, `_aligned_malloc(64 KiB, 64 KiB)` | 46 | 6,030,160 | 31.89% |
| `malloc(64 KiB)` — 46 x (65,536 + 16) | 46 | 3,015,392 | 15.95% |
| **released** | 0 | **3,014,768** | **15.94%** |

> table's 3,014,768 and the exact-granule 3,014,656 is the same unattributable
> extra-granule residue at 46 chunks; after the merge it is **±16 x chunks**

>
> **LANE MARKER on the block immediately above, and it lands on one

Against the uninstrumented denominator of 18,203,808 B the same change is
**16.56%**. `posix_memalign` on the other arm already allocates exactly
65,536 and wastes nothing, so **this is a Windows-only tax**, and dropping
the alignment removes the platform split rather than widening it.

**Three things a repair slice must carry, none of them optional:**

1. **The chunks move into the `HCSIZE 65536` row.** That row is
   `DECOMP-ON.md` §1's A1, attributed as *"114 of the 118 blocks are
   cycle-collector arena chunks"*. After the change it would read 164 blocks,
   and that attribution would be wrong without a word. Two arenas sharing one
   chunk size is a reader hazard, and this corpus has paid for an unannounced
   one before.
2. **`scr_str_chunk_free` must change in the same edit.** `_aligned_free`
   recovers the original pointer from `((void **) p)[-1]`; handing it a plain
   `malloc` block frees a wild pointer.
3. **It is not a `VirtualAlloc` job.** Windows' allocation granularity is
   64 KiB, so `VirtualAlloc` would also return an aligned chunk with no
   padding — but it would take the chunks off the CRT heap entirely, out of
   the census and out of every fragmentation number this corpus has, for a
   saving `malloc` already delivers. And it would need `windows.h` or the
   `__asm__`-name declaration trick `scr_heap_census.h` uses for `HeapWalk`.
   The cheap change is the right one.

## 6. The overhead column solves exactly, which closes a control limitation

`DECOMP-ON.md` §4 ends by writing down that the exactness of 131,079 rests on
indirect evidence: *"The two rows that dominate the `on` arm, 65,536 and
131,079, are backend blocks and were never covered by that control"* —
`busyband.c` plants only 1,288..4,384. The overhead column closes it.

`scr_heap_census.h` accumulates `scr_hc_tbl[j].bytes += size + overhead;`
from `HeapWalk`'s `cbData` and `cbOverhead`, so `bytes - size*n` is the sum
of the per-block overheads. The model that fits the whole census is
`granule = round16(request + 8)`, `overhead = granule - request`:

| row | predicted overhead | arm | solves as |
|---|---:|---|---|
| `HCSIZE 24 6429` | 8 | `on` | 6,429 x 8 = 51,464 ✓ |
| `HCSIZE 131072 1` | 16 | `on`, `long`, `half-on` | 16 ✓ (`off` carries one extra granule) |
| **`HCSIZE 131079`** | **9** | `on`, `off` (46 blocks) | 39 x 9 + 7 x 25 = **526** ✓ |
| | | `long` (46 blocks) | 41 x 9 + 5 x 25 = **494** ✓ |
| | | `half-on` (33 blocks) | 29 x 9 + 4 x 25 = **361** ✓ |

A request of 131,079 predicts overhead 9; the arms solve to 9, with a few
blocks carrying one extra 16-byte granule, in integers, three times. **Had
`HeapWalk` been rounding `cbData` to a bucket, the overhead would have been
16 and the sums would read 736, 736 and 528.** They read 526, 494 and 361.
`cbData` is the request.

## 7. The instrument that was designed and NOT built

The slice was ordered as a HeapWalk-side content reader, and the table below
is the design. **It was not written, not compiled and not run**, because §0
closed the question first. It is recorded so the next reader knows what was
skipped and why, and because its predicted signature is now a falsifiable
claim rather than a hypothesis.

| candidate | predicted signature in the first 64 bytes |
|---|---|
| arena, freshly committed | all zero, and a zero tail to the end of the block |
| arena with a header | a small struct, then zeros; a self-pointer into the block |
| refcounted object | a small integer (1..few) in the first or second word |
| text buffer | printable ASCII |
| compressed or socket payload | high-entropy bytes, no structure — **the design's own failure mode** |
| **an aligned-allocator block** | **nothing at offset 0**; the structure starts at the next 64 KiB boundary inside the block, with the original pointer stored in the 8 bytes below it |

The last row is what the chain in §0 predicts, and it is why a reader of *the
first* 64 bytes would have come back with garbage: at offset 0 there is only
whatever `malloc` left behind. **The brief that ordered this slice registered
exactly that risk — that the bytes might not say who allocated — and it was
right, for a reason it did not name.**

A probe that would confirm §0 in one run, if one is ever wanted, is two
comparisons and no dump. Inside `scr_heap_census.h`'s existing walk, for a
busy block of `cbData == 131079` at `lpData`:

```
p = (lpData + 8 + 65535) & ~(uintptr_t)65535     /* the aligned chunk       */
((void **) p)[-1] == lpData                      /* mingw/UCRT back-pointer */
*(unsigned long long *) p == 0x5343525f53545243  /* SCR_STR_CHUNK_MAGIC     */
```

**Footprint: zero heap bytes.** It reads memory the walk already holds a
pointer to, and it allocates nothing. Its only cost is output, and that
output must be buffered in `SCR_HC_SHARED` storage and printed **after**
`scr_hc_HeapUnlock` — an `fprintf` inside the walk can fault the stdio buffer
into `malloc` on the heap it has locked. **It moves the answer by nothing**:
it can only falsify §0, which the arithmetic and §4's bracket already make
expensive to doubt.

Its positive control is already planted and costs nothing extra: the census
arms itself with `SCR_HEAPCEN_ARM` blocks of `SCR_HEAPCEN_ARM_SIZE` and does
`memset(arm[i], 0x5a, 16)` before walking. A reader pointed at the 5,113 band
**must** print sixteen `5a` bytes. A band that reads empty while the arm band
reads `5a5a...` is an absence; a band that reads empty while the arm band
also reads empty is a dead reader. Neither arm alone says which.

## 8. What this does not say

* **It does not say the arena is too big.** 46 chunks x 64 KiB = 2.875 MiB of
  string storage, and their internal occupancy is not measured here — the
  same gap `DECOMP-ON.md` §1 declares for the cycle arena. **Only the padding
  is established as holding nothing.** The arena itself is neither a lever
  nor a non-lever on this evidence.
* **It does not retract anything in `DECOMP-ON.md`.** §4's exclusion chain is
  correct at every step; its conclusion *"at least 42 of 46 are outside the
  prof lane entirely"* is now **46 of 46**, and its hole 2, libc, is the one
  that was holding the answer.
* **The `on` arm is a proxy**, per `DECOMP-ON.md` §0, and every number above
  inherits that. The row is byte-identical on `off`, which is not a proxy, so
  nothing in §1 turns on it.
* **No measurement in this file is new.** Every census and prof figure is
  read from `evidence-idle/` as committed.
