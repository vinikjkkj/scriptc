and :1061 macro-replaces calloc with it; the body calls
SCR_PROF_NOTE_STACK(r, a * b) -- the PRODUCT, which is the request size and
therefore the census class exactly (scr_heap_census.h:317 notes cbData).

would have been "not instrumented", not "no such site". It does not.

--- 4. WHICH PATH -- which is what a file:line does not say ------------

  A  8 x   934,576  scr_bytes_alloc <- [runtime TU, unmapped] <- .. <- main
  B  8 x 1,048,576  scr_bytes_alloc <- ProtoStreamReader_ensure+2024
  C  8 x   934,576  scr_bytes_alloc <- scr_bytes_copy+27 <- .. <- main
  D  1 x 1,048,576  .. <- wsSendText <- wsOffer <- wsCatchUp <- wsAttach

B is the decisive one: sc_tr__x25__x25_m41_ProtoStreamReader_ensure is the
protobuf stream reader growing its read buffer, and it reaches
scr_bytes_alloc DIRECTLY -- one 1 MiB Buffer per chunk. C is
scr_bytes_copy (scr_bytes.c:79, scr_bytes_alloc(src->elem, src->len)) --
a COPY of a 934,576-byte payload. A and C share their inner suffix
(2035a9 202f5b 16e1a2 1a30bc9), so the 934,576 pair is ONE producer reached
two ways, not two independent buffers: a payload produced once and copied
once, at the SAME length.

That settles "one object with two allocations vs two independent buffers
per chunk" (86613275d s.7) in the FIRST direction, for 934,576 only.
D is a DIFFERENT site -- its frames 0 and 1 fall outside scr_bytes.obj --
on the websocket send path, and it is 1 allocation, not 8.

WHY 6-7 LIVE BLOCKS AT THE PEAK: 8 chunks decode concurrently and each
holds a 1 MiB reader buffer plus a 934,576-byte payload plus its copy. The
count is the chunk fan-out, not a cap, and the burst drains as chunks
retire -- which is why all of these classes have NO LINE AT ALL in the
shutdown census.

--- 6. CONTROLS -------------------------------------------------------

POSITIVE CONTROL: not needed, and that is a statement about the result and
not a skipped step. The band did not read zero -- it read 25 allocations
and 24,390,400 bytes in BOTH runs. The previous build sizeband2=4376..4376
captured 2,780 allocations of exactly 4,376 B, so the mechanism was known
live; this run shows it live on two new sizes.

EXACTNESS: bytes/count is an integer equal to a band edge in every row. A
row mixing sizes would show a fractional mean. None does.

NEGATIVE: tablefull=0 and lost=0 in both runs, so no row is a sample of
whatever ran first, and no admitted allocation failed to key to a stack.

WHAT THIS DOES NOT SHOW. skipped= is about 10.5 million: the band is a
FILTER and these 25 stacks are not a census of the program. The claim is
about the two named classes only.

FLUX vs RETENTION. PROF counts the whole run, so 25 allocations over a run
is a FLOW. That they are simultaneously LIVE at the peak is the separate
HCPKSIZE evidence of 272390bd2, not something this band measures.
