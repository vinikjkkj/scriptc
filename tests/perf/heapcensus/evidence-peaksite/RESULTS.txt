--- 4. ELIMINATING scr_string.c:1217 BY THE SHAPE OF ITS REQUEST -------

Two sites carry octaves 19 AND 20. They are separated by ARITHMETIC, not
by plausibility:

  scr_bytes.c:52   b->data = calloc(len ? len : 1, scr_bytes_elem_size(elem));
     request = len * elemsize, EXACT. A Buffer of 1,048,576 bytes asks
     for exactly 1,048,576. Any class value is reachable.

  scr_string.c:1217  realloc(s, scr_pool_bytes(sizeof(ScrStr) + newcap + 1))
     sizeof(ScrStr) = 12 (three uint32_t + char data[], scr_runtime.h:754)
     SCR_POOL_GRAIN = 8          (scr_runtime.h:359)
     scr_pool_bytes(n) = (n+7) & ~7   (scr_runtime.h:433)
     => request = roundup8(newcap + 13).
     Its only caller is scr_jb_grow, whose buffer DOUBLES from 64
     (scr_string.c:1194-1196, in the comment on the carve predicate), so
     newcap = 2^k and the request is 2^k + 16 for every k >= 4.

  So scr_string.c:1217 CANNOT produce a 1,048,576 request. It produces
  1,048,592. Prediction: classes of the form 2^k + 16 must exist in the
  census (the builder is real and does grow), but must stop below the
  megabytes if its big buffers are not live at a census instant.

      p = SQLITE_MALLOC( nByte+8 );   /* then p[0]=nByte; p++ */
  which is the "+8" of WHICH-BUFFER.md's 4096 + 216 + 56 + 8 = 4376.

named this as the likeliest way the whole search returns a false null.
Site families in sb.prof.txt:
     136 sites  runtime/src
       3 sites  other
       2 sites  vendor/sqlite
       1 sites  vendor/zlib

  => vendored sqlite AND zlib both register sites. The feared blind spot
     does NOT exist for them, and the single most load-bearing
     attribution in this file (4,376 = sqlite page cache) rests on a
     VENDOR site. The positive control discriminates and it passes.

NEGATIVE CONTROL -- is there a live census class with NO site in its
octave? If PROF were blind to a path, a class it owns would show up here.
Every peak class of p1 with n >= 4, against the sb site table:
    (none)
    orphan classes: 0, 0 bytes;
    covered classes bytes: 46205984
    => 100.00% of peak bytes in classes with n>=4 sit in an octave PROF registers.

  THIS CONTROL IS WEAK AND SAYS SO. An octave is 1 doubling wide, so
  "some site allocates in this octave" is a low bar and a pass here is
  NOT proof the class's own site is registered. It can only FALSIFY.
  It did not falsify. That is all it is worth.

A CONTROL THAT DID NOT DISCRIMINATE, stated rather than buried: PROF
outstanding (count - freed) vs the census busy-block count.
    sb PROF: count=10538785 freed=10319997 => outstanding=218788
    sb census at shutdown: blocks=47940  (sb.heapcen.txt, HCTOTAL)
    ratio 4.56x
  PROF reports 4.6x MORE outstanding than the heap holds blocks, which is
  the wrong direction for a blind spot and so cannot measure one. The
  cause is that PROF counts logical allocations the string arena and the
  pool serve by carving and recycling, which never become distinct CRT
  blocks. This control is reported because it was run, and it discriminates
  NOTHING about coverage.

  run   1,048,576   934,576   mode
  p1            6         6   low
  p2            6         6   low
  p3            6         6   low
  p4            7         7   HIGH
  p5            6         6   low
  p6            7         7   HIGH

  The two classes agree on the mode in all six runs, and neither ever
  reads 8. The explanation is NOT from this slice -- it is the phase
  trace quoted in PEAK-OCCUPANT.md section 4, from the evidence-peak runs:

     abba1A  chunk-decoded-1 20.995 | 2..7 all within 6 ms at 27.68 | 8 at 28.408
     abba3B  chunk-decoded-1 20.972 | 2..8 all within 5 ms at 29.27

  All eight chunks are SENT inside 191 ms; the client holds and decodes
  them in one burst ~7 s later. Chunk 1 always decodes alone at ~21.0 s
  and is released long before the burst. The burst is then chunks 2..7
  (six) or 2..8 (seven). The peak census samples inside that window.
  So 8 chunks = 1 early + (6 or 7) concurrent: the census never sees 8
  because chunk 1 is never concurrent with the rest.

  CROSS-RUN: that trace is from evidence-peak (a different build and a
  different set of runs). It explains the SHAPE 6/7-not-8 that p1..p6
  show; no number is carried across.

--- 8. WHAT IS AND IS NOT ESTABLISHED ----------------------------------

ESTABLISHED
  * 4,376 = SQLite page cache, vendor/sqlite/sqlite3.c:28035
    (sqlite3MemMalloc, the nByte+8 path). Evidence is THREE-fold and the
    strands are independent: the octave-12 site table, a stack-capture
    band armed on exactly 4376..4376, and the source arithmetic
    4096+216+56+8. This one is not a size coincidence. The two sites that
    OUTRANK it in the octave are both eliminated by arithmetic:
    scr_array.c:444 can only request powers of two (cap doubles from 4,
    want = cap*8), and scr_heap_census.h:707 is the instrument's own
    5113-byte arm, corroborated by HCTOTAL armSize=5113 armCount=137.
  * scr_string.c:1217 is ELIMINATED for both megabyte classes, by the
    arithmetic of its own request expression plus the absence of every
    2^k+16 class above 65,552 from all twelve census instants.
  * The census class label is the REQUEST (cbData), exactly; no overhead
    term stands between a PROF size and a census class.

NOT ESTABLISHED
  * That scr_bytes.c:52 IS the site of 1,048,576 and 934,576. It is the
    ONLY SURVIVING CANDIDATE among registered sites, which is stronger
    than a size match, but it is still an elimination over the set PROF
    registers -- and the octave is a doubling wide, so "scr_bytes.c:52
    allocates somewhere in [512K,1M)" is not "scr_bytes.c:52 allocates
    exactly 934,576". NO stack band was armed on these sizes, so there is
    no second strand. Call it a leading candidate, not a naming.
  * WHY the 1,048,576 class carries overhead 0 and 934,576 carries 16.
  * Whether the pair is one logical object or two. The counts move
    together in all six runs and the mode agrees, which is consistent
    with a pair, but co-movement under a shared driver (the chunk burst)
    is exactly what two INDEPENDENT per-chunk buffers would also show.
    This cannot separate those.

WHAT WOULD CLOSE IT, and it is cheap
  sb-build.sh:16 already carries the mechanism:
    -DSCR_PROF_STACK_SIZE_MIN2=4376 -DSCR_PROF_STACK_SIZE_MAX2=4376
  One rebuild with
    -DSCR_PROF_STACK_SIZE_MIN=934576  -DSCR_PROF_STACK_SIZE_MAX=934576
    -DSCR_PROF_STACK_SIZE_MIN2=1048576 -DSCR_PROF_STACK_SIZE_MAX2=1048576

--- 9. VERDICT ON THE PREREGISTERED PREDICTION -------------------------

Predicted, before this slice ran: "1,048,576 and 934,576 are a PAIR --
a decode/stream buffer allocated per in-flight history-sync chunk, one
sized by a CONSTANT and the other DERIVED from it."

  (a) PAIR, in the sense of co-moving: SUPPORTED. Same count and same
      mode in all six runs (section 7), and PEAK-OCCUPANT.md section 4
      reports the same agreement on its own four runs.
  (b) PER IN-FLIGHT CHUNK: SUPPORTED but not by this slice. The count
      equals the burst width from the phase trace, which is another
      slice's measurement. Here it is consistency, not evidence.
  (c) A DECODE BUFFER: the surviving candidate scr_bytes.c:52 is the
      Buffer / typed-array payload store, which is the right KIND of
      object. Still an elimination, not a naming -- see section 8.
  (d) "ONE SIZED BY A CONSTANT, THE OTHER DERIVED FROM IT":
      NOT SUPPORTED, and this is the half that fails.
      1048576 = 2^20 exactly -- constant-shaped. Fine.
      934576 = 2 * 2 * 2 * 2 * 58411  -- its odd part is 58411, prime.
      a - b = 114000;  b/a = 0.891281128;  a/b = 1.121980449
      No power-of-two ratio, no round difference, no shift-and-add of
      the 1 MiB figure lands on it. 934,576 looks like a DATUM (a
      payload length that is what it is), not a size derived from a
      cap. The pair co-moves because one driver produces both, which
      is a weaker claim than "derived from".

  AND THE CO-MOVEMENT CANNOT BE PUSHED FURTHER. Two independent
  per-chunk buffers driven by the same burst produce exactly the same
  lockstep as one object holding two allocations. This slice has no
  column that separates those, and the overhead reading (0 vs 16) is a
  hint in the OTHER direction that was not followed up.
