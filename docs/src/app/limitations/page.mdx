# Limitations

Honesty is the product. The static surface is large but not total, and a few behaviors diverge from Node **by design**. This page is the plain-language version; `scriptc coverage` on your program is the real answer for your code, and every blocker it reports is specific and coded. Nothing on this page is silent: everything here is either a compile error or a documented, numbered divergence.

## What doesn't compile (yet)

These are rejected at compile time with an `SC` code, a code frame, and usually a rewrite hint. A non-exhaustive tour of the ones you're most likely to meet:

**Language edges**

- `var` declarations, and loose equality `==`/`!=` (they need dynamic coercion semantics; use `let`/`const` and `===`).
- Labeled `break`/`continue`, and jumps crossing a `finally` block (`return` through `finally` is supported).
- Generic classes, generic methods, and generic arrows — only top-level generic function declarations monomorphize.
- Generic functions and stdlib methods used as *values* (`const f = id`, `const g = Math.floor`) — call them directly.

**Types and shapes**

- **Record shapes are exact structs.** Passing `{a, b}` where `{a}` is expected is SC2002. Where the compiler does accept a strict field-subset flow, it copies the record — see divergences below.
- Union edges: unions used whole where a per-arm answer is needed (reading `u.length` on `string | string[]` — narrow first), union-into-union widening outside the re-tag and width rules, function arms beside data arms. (Printing a whole union is fine: `console.log(u)` dispatches per arm.)
- Watch for **tuple inference**: `Promise.all([work(1), work(2)])` infers a tuple type, and tuple edges (like `.join` on a tuple) are fenced. Type the array first:

```ts
const jobs: Promise<number>[] = [work(1), work(2), work(3)];
const results = await Promise.all(jobs); // number[] — compiles
```

- `undefined`/`null` exist only as union arms, not as standalone values; optional *class* fields are fenced (optional record fields and optional/default/rest parameters compile).

**Standard library**

- The type checker sees the full standard library; only the supported surface compiles. Reaching declared-but-unlowered surface is SC2020 with the supported alternatives in the hint — e.g. parts of the regex API (`re.exec`), `Symbol`, array/Map/Set methods beyond the lowered sets, and `globalThis` members beyond the globals this runtime provides.
- Reading a property of `globalThis` that this host does not have answers `undefined`, like every JavaScript host — `(globalThis as { gc?: () => void }).gc` is `undefined` here exactly as it is under Node without `--expose-gc`. The fold needs a DECLARATION that admits the absence (`declare var gc: ... | undefined`) AND a site with somewhere to put it, so a member declared non-optional keeps its fence and names the one-character fix. A name nothing declares does not qualify: the declarations say what scriptc supports, not what the host has.
- `process.memoryUsage()` is refused: four of its five fields (`heapTotal`, `heapUsed`, `external`, `arrayBuffers`) are V8 heap statistics and a compiled binary has no V8 heap, so `0` would read as a measurement. `process.memoryUsage.rss()` lowers — Node's own single-value spelling of the one field that is an operating-system fact.
- **`node:inspector` and `node:inspector/promises` are refused, and will stay refused.** They drive the V8 inspector protocol — debugger, profiler, heap access — and a compiled binary embeds no V8 to inspect. This is not a lowering that has not been written; there is no subject for it. A no-op `Session` would be worse than the refusal: the usual shape is `JSON.stringify((await session.post('Profiler.stop')).profile)` written to a `.cpuprofile`, which a stub turns into an empty file and a cheerful log line at exit 0. The import is SC1010, a compile error, so no `try`/`catch` around the profiling call can shelter it. Profile the Node run, or measure the binary from outside — `process.memoryUsage.rss()` and `perf_hooks` do lower.
- `process.on("uncaughtException", ...)` is refused: an escaped throw prints `Uncaught <error>` and exits 1 at the throw, so a listener could never run and the loop never resumes, where Node calls the listener and continues. `process.on("exit", ...)` DOES fire on that path with code 1, and `"unhandledRejection"` covers an escaped promise.
- Map keys and Set elements are strings and numbers; other key types are fenced.

**The `any`/`unknown` boundary**

- `any` without `--dynamic` is a compile error (SC2011) — use `unknown` and a checked cast, or opt into the engine.
- `any` and `unknown` ride locals, parameters, and returns — never class fields, array elements, or union arms (record and tuple fields hold `unknown`).
- Operations on `unknown` beyond the supported surface (truthiness, `typeof` narrowing, property access, `+`, `switch`, `throw`) need a checked cast first.

**Type surface**

scriptc typechecks your program in its own type world: the standard `es2025` lib plus its own ambient declarations. In enumerated places those declarations are deliberately different from stock lib or `@types/node`, typed as what actually compiles — `JSON.parse` returns `unknown` (not `any`), `pop()` returns `T` (not `T | undefined`), the Promise executor's reject reason is pinned to `Error`. So "programs that typecheck" means scriptc's type world, and a program clean under its own `tsc` can still be redirected here — but never with a bare type error it can't reproduce: the tightened declarations get a second-chance preflight (a program clean in the project's own type world passes, and the affected sites meet per-site diagnostics with rewrite hints instead), and where the shipped fallback declarations lack a lowering for a stock member (`console.table`, `console.time`, ...), the member is declared anyway so the call lands on SC2020 naming the supported alternative. `console.log`/`info`/`debug`/`error`/`warn` themselves take `unknown` arguments and render with Node's console semantics — strings verbatim, everything else through the static `util.inspect`.

Run `scriptc build` on a file to get the full, current list for that program — the compiler is always more up to date than this page.

## What diverges by design

A static-tier program otherwise produces byte-identical stdout and the same exit code as Node. Every known divergence is deliberate and pinned by the differential test suite; these are the ones with real consequences:

**Arrays are dense — invalid indices trap.** scriptc arrays have no `undefined` elements. Where JS would produce `undefined` (out-of-bounds read, `pop()` on empty), the runtime prints a `RangeError` message and aborts. A slot can be EMPTY — `Array.from({ length: n })` makes n of them, growing `a.length` appends more, and the queue idiom `a[i] = null as unknown as T` clears one so the array stops retaining the item — and copies carry an empty slot through (`slice`, spreads, `copyWithin`, `fill` over it), but READING one is a trap naming the index and the length, not `undefined`. This catches real bugs — but it means `process.argv[2]` with no third argument is a trap, not `undefined`:

```ts
// JS habit — traps when argv[2] doesn't exist:
const who = process.argv[2] ?? "world";
// scriptc-safe (the length check is explicit instead of implied):
const who = process.argv.length > 2 ? process.argv[2] : "world";
```

**Runtime traps are not catchable.** User `throw` is fully catchable, and runtime failures Node models as exceptions (JSON parse errors, checked-cast failures, fs errors, regex errors) throw real error objects — but the hard-trap set (array index violations and friends) aborts the process rather than throwing.

**`require()` with a run-time specifier refuses, and the refusal is not catchable either.** A compiled program's module graph is fixed at build time, so a `require` whose specifier is only known at run time has no answer to give: the value would have to be a module namespace object, and there is no dynamic loader to produce one. What the binary CAN decide it still decides — a specifier nothing installed resolves throws Node's own catchable `MODULE_NOT_FOUND` at the require site, and Node's argument errors (`''`, a non-string) arrive as catchable `TypeError`s, so the optional-dependency idiom keeps working unchanged. For every other specifier the site prints the refusal, naming the construct and the source position, and exits non-zero.

It is deliberately not catchable, and the reason is the idiom itself. protobufjs's `inquire()` — which every protobuf bundle ships — is `try { return require(m) } catch (e) {}` followed by `return null`, so a catchable refusal was swallowed there and `require("buffer")` answered `null` where Node answers a module, at exit 0 with nothing reported. A refusal a program can mistake for an answer is worse than no refusal at all.

**A lying cast on dynamic data throws instead of corrupting memory** — the headline divergence, and the point. `JSON.parse(s) as Config` with mismatched data throws a catchable error naming the offending path (`expected number at $.port, got string`) where JS would silently hand you garbage.

**Structural width subtyping copies.** A record flowing into a strict field-subset shape is copied, not aliased: mutations through the narrower reference are invisible to the original. Same stance at the dynamic boundary: values cross by copy, never by reference. The copy also *ends* the properties outside the narrower shape — a record's type is its runtime shape here, so a value that reaches a narrower declared type (a `const` annotation, a parameter, a declared return type) no longer carries the fields that type does not name, and a later cast back to a wider shape completes them as `undefined` rather than finding the originals. JS keeps them:

```ts
type Narrow = { get(): number };
type Wide = { get(): number; extra?(): number };
function mk(): Narrow {
  const rich = { get: () => 7, extra: () => 1 };
  return rich;            // the copy into Narrow drops `extra` here
}
(mk() as Wide).extra;     // scriptc: undefined      Node: the function
```

Only *optional* members complete this way — a required one has no `undefined` to complete to, and the cast is refused at compile time instead.

**In a JavaScript source this does not apply to a binding that simply NAMES an object.** `const ns = { v: 1 }` at a JS file's scope holds a dynamic object — JS object identity is the literal's contract — and `const a = ns` keeps it rather than materialising a record from it, so `a === ns` is true and a write through either is seen by both, exactly as in Node. The width copy above is TypeScript's stance, where the narrower shape is an annotation the author wrote.

**`Object.keys`/`values`/`entries`, `for...in`, object spread and `JSON.stringify` all report a record's declaration order**, not per-object insertion order — one order source, so no surface disagrees with another. Identical to Node whenever objects are built in declaration order (the overwhelmingly common case). Where the compiler can SEE a construction that is not — a literal spelled another way, a literal holding a spread, one returned from a function, or a record filled by later field writes — enumerating it is a compile-time refusal naming the order it would have answered, not a silent wrong object. One construction still answers: a record materialised out of a DYNAMIC value (`JSON.parse(s) as T`), whose source order is a run-time fact no struct carries. That reports the shape's order with an `SC6002` advisory. Its key SET is per-instance and correct; only the order is the shape's. A shape's enumeration order is a CHOICE, and where your program proves one the compiler takes it: if every construction of a shape is a literal, and they all spell it the same way, that spelling becomes the shape's order and all six surfaces answer Node exactly — an order the declared type never had (a `Record<K, V>` or any other mapped type has no member list in the source at all) is no obstacle. The refusal's remaining domain is an order that is not KNOWABLE: two literals spelling one shape differently, a literal with a computed name or a conditional spread, a record filled by later field writes, or a shape a checked cast materialises. Reordering the literal is then not always available as a fix either: `declaredOrder` belongs to whichever type interned the shape first, so a second literal over the same members inherits it — read the fields you need instead of enumerating when that happens.

**Strings are stored as UTF-8.** Invisible through `.length` and the string methods (which compute UTF-16 semantics) — except relational comparison (`<`, `>`), which uses code-point order, and surrogate-splitting operations, which produce U+FFFD.

**Memory is reference-counted.** Acyclic values free deterministically; reference cycles are collected at deterministic collection points, not by a concurrent GC. Cycles that cross the static/island boundary are uncollectable by either side.

**Process shape** — `process.argv[0]` is `"scriptc"` and `argv[1]` is the binary's path (positions line up with Node; `argv[2]` onward are your args). The uncaught-exception stderr line reads `Uncaught <value>` instead of Node's stack-trace block (exit code and pre-throw stdout are identical). Runtime errors carry `message` and Node's `code`, but not `errno`/`syscall`/`path`.

**Comparator call sequences differ in `sort` and `toSorted`** (stable insertion sort here, TimSort in V8 — sorted results are byte-identical for consistent comparators), and **`localeCompare` compares code units**, not ICU collation. Locale *data* stays outside the runtime, but the locale *name* does not: `Intl.DateTimeFormat().resolvedOptions().locale` reads the machine's default locale tag at runtime (`GetUserDefaultLocaleName` on Windows, `LC_ALL`/`LC_MESSAGES`/`LANG` in ICU's order elsewhere, `en-US` for the C locale — V8's own fallback). A POSIX `@modifier` is dropped rather than folded into a script or variant, and the other `resolvedOptions()` members fence.

## Dynamic-tier limits

- **The island is quickjs-ng, not V8** — correct, but slower for CPU-bound dependency code. The win is startup, size, memory, deployment shape.
- **The island's Node builtins are shims** — reimplementations, reported per-builtin in the coverage report, not the real modules.
- **Island microtask interleaving**: static fibers drain first, then the engine's jobs at loop quiescence — a static `await` racing a package promise resolves in a documented, deterministic order that can differ from Node's interleaving.
- **Top-level `await` in embedded ESM packages** is not supported yet. It does compile in your program's own ESM graph and in npm packages compiled through `--npm-static`; the remaining limit is package code running inside the `--dynamic` island.
- **`--npm-static` and `--provenance-sources` are experimental** — see [npm Dependencies](/dependencies) for the maturity notes.
- **Cross-compiled `--dynamic` binaries are not supported yet** — the engine archive is host-native today.

## Tooling gaps

- `scriptc run` does not forward extra CLI arguments to the program — `build` and invoke the binary directly.
- Native FFI is a direct, manifest-declared C ABI link surface. It does not yet support callbacks, variadic calls, structs by value, owned pointer/string/byte returns, runtime dynamic-library loading, or library-mode builds. See [Native FFI](/ffi).
- Numbers are JS-exact f64 everywhere. Integer inference and ownership analysis — the systems-language performance ceiling — are roadmap, not shipped.
- No Windows servers or `child_process` yet — see [Platform Support](/platforms).
